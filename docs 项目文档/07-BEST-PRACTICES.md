## 二、Spec-First Development (Ashpreet)

### 核心理念

> "软件工程不是编写代码，而是管理复杂性。"

### 目录结构

```
specs/[feature-name]/
├── design.md          # 设计文档 (Source of Truth)
├── implementation.md  # 进度追踪 (支持会话恢复)
├── decisions.md       # 架构决策记录 (ADR)
├── prompts.md         # 可复用提示词库
└── tests/             # 功能测试用例
```

### AliciBlog 适配

```
/reports/[YYYY-MM-DD]-[topic-slug]/
├── 00-implementation.md   # 进度追踪 ← 必须
├── 00-topic-scout-report.md
├── 00-topic-brief.json
├── 01-article-draft.md
├── 02-chinese-preview.md
├── 03-aeo-score.md
├── 04-article-improved.md
└── 05-article-final.md
```

### 关键实践

| 实践 | 描述 | 好处 |
|------|------|------|
| **Symlink 到项目根** | `ln -s specs/feature PROJECT_ROOT/feature` | 便于导航 |
| **Cookbooks** | 每个功能必须有可运行示例 | 验证可行性 |
| **版本控制** | Git 跟踪所有 spec 文件 | 决策可追溯 |

原则: 所有任务从 Plan 开始，反复讨论直到满意

## 四、上下文管理 (7年SWE)

### 30% 警戒线

```
上下文使用:  0%────30%────50%────100%
质量曲线:    ████████▓▓▓▓░░░░░░░░
             最佳区间  退化开始  严重退化
```

**应对策略**:
- 超过 30% 使用 `/compact`
- 复杂任务拆分为多个会话
- 使用外部文件作为记忆存储

### 外部记忆

| 文件 | 用途 | 更新时机 |
|------|------|----------|
| `implementation.md` | 进度追踪 | 每个阶段完成后 |
| `SCRATCHPAD.md` | 临时笔记 | 思考过程中 |
| `decisions.md` | 架构决策 | 重要选择后 |
| `plan.md` | 任务规划 | 任务开始时 |

### Think First

```
错误流程: 需求 → 立即编码 → 返工
正确流程: 需求 → 深度思考 → 规划 → 一次完成
```

**思考检查表**:
- [ ] 任务边界清晰？
- [ ] 依赖项明确？
- [ ] 验证方式确定？
- [ ] 可能的坑预判？

### 输入质量

> "Bad Input = Bad Output"

**AliciBlog 应用**:
- Topic Brief 质量把控
- 素材来源验证
- 竞品内容筛选

## 六、反模式 (Don'ts)

### 绝对不要

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| 跳过 Plan 模式 | 返工风险高 | 先规划后执行 |
| 单会话处理多功能 | 上下文污染 | 一个会话一个主题 |
| 忽略 AEO < 75 | 质量失控 | 必须改进或人工审核 |
| 手改 implementation.md | 追踪失效 | 让 Claude 自动维护 |
| 使用营销词 | 可信度下降 | 保持专业客观 |
| 无 Brief 直接写 | 内容跑偏 | 必须先有 Topic Brief |

### 警惕信号

- 上下文使用 > 30%
- 同一问题问两次
- Claude 开始重复自己
- 输出质量明显下降

## 十、输入质量控制 (7年SWE 新增)

> "Bad Input = Bad Output" — 十次里有十次，用规划模式产出的效果都显著优于直接开聊

### 提示词优化原则

| 原则 | 差的示例 | 好的示例 |
|------|----------|----------|
| **具体化** | "帮我建一个认证系统" | "基于现有 User 模型实现邮箱/密码认证，用 Redis 存储会话（24小时过期），添加中间件保护 /api/protected 路由" |
| **约束化** | "写一个功能" | "保持简单，不要添加我没要求的抽象" |
| **说明原因** | "用 Redis" | "用 Redis，因为我们需要跨实例共享会话状态" |

### 模型选择策略

| 模型 | 适用场景 | 特点 |
|------|----------|------|
| **Opus 4.5** | 规划、架构、复杂推理 | 更深思考，更少引导 |
| **Sonnet** | 路径清晰的执行任务 | 更快更便宜 |

**推荐工作流**:
```
Opus 做规划和架构决策
        ↓
切换到 Sonnet 做实现
        ↓
CLAUDE.md 确保模型在同样约束下运行
```

### 卡住时的处理

当 Claude 进入死循环时，不要继续推进：

1. **清除对话** - `/clear` 给全新开始
2. **简化任务** - 拆成更小的部分
3. **展示而非讲述** - 给最小示例
4. **发挥创意** - 换个角度表述

> "如果你解释同一件事三次 Claude 还是不理解，更多解释不会有帮助。改变点什么。"

## 十一、系统化思维 (7年SWE 新增)

### 构建系统而非一次性任务

从 Claude 获得最大价值的人，不是用它做一次性任务——他们在构建以 Claude 为组件的系统。

**飞轮效应**:
```
Claude 犯错
    ↓
审查日志
    ↓
改进 CLAUDE.md 或工具
    ↓
下次表现更好
    ↓
(复利效应)
```

### CLAUDE.md 的本质

> "好的 CLAUDE.md 像你知道自己明天会失忆时给自己留的备忘录。"

**检查标准**:
- [ ] 简短（<200行）
- [ ] 针对项目定制
- [ ] 说明原因，不仅是做法
- [ ] 持续更新

## 十二、核心要点速查

| 要点 | 说明 |
|------|------|
| 先思考再动手 | 规划产出效果远胜直接开聊 |
| CLAUDE.md 是杠杆 | 简短、针对性强、说明原因 |
| 上下文 30% 退化 | 用外部记忆，限定对话范围 |
| 架构最重要 | 不能跳过规划 |
| 输出来自输入 | 烂结果 = 提示词需要改进 |
| 卡住就换方法 | 不要死循环 |
| 构建系统 | 让改进随时间复利 |
