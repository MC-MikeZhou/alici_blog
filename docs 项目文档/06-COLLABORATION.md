# 06 - 协作模式：从人驱动到 Agent 驱动

> 回应 Sam 关于 Git 协作的讨论，从增长目标重新理解协作问题

---

## 一、先对齐目标

Sam 的讨论聚焦在"多人如何同步文件"，但这只是冰山一角。我们真正要解决的是**增长问题**。

### 增长问题的三个层次

| 层次 | 问题 | 传统解法 | Claude Code as OS 解法 |
|------|------|----------|----------------------|
| **产品交付** | Demo 卡在开发手里 | 等开发排期 | PM/设计师直接用 Claude 做 Demo |
| **内容驱动** | 系统无法自动运转 | 堆人力 | Skills + SOP 让 AI 驱动 |
| **知识沉淀** | 隐性知识在脑子里 | 写文档（但没人写） | Agent 自动沉淀、自动编写 |

### Sam 讨论的位置

```
增长问题
├── 产品交付效率
├── 内容驱动自动化
├── 知识沉淀与传承
│
└── 协作基础设施  ← Sam 在这里
    ├── Git 并行
    └── 文件同步
```

基础设施重要，但不是目标本身。

---

## 二、Sam 判断正确的部分

Sam 的分析在执行层面完全正确：

| 观点 | 评价 |
|------|------|
| Git 是并行协作协议，不只是存储工具 | ✅ 正确 |
| Zip 传递会导致上下文丢失 | ✅ 正确 |
| 没有 Git 就只能瀑布流单线程 | ✅ 正确 |
| Git 能减少合并工作量 | ✅ 正确 |

Sam 举的场景也很准确：
```
Hans、Dancy、Petty 各自与 Claude 讨论后上传 Zip
→ Sam 下载 Hans 的版本继续
→ 丢失了 Dancy 和 Petty 的上下文
→ 来回几次后，没人知道哪个版本完整
```

**Git 确实能解决这个问题。**

---

## 三、需要补充的上下文

Sam 的讨论暗含一个假设：

> 每个人都需要亲自与 Claude 讨论，然后合并大家的讨论结果。

但在 Claude Code as OS 的范式下，这个假设本身需要重新审视：

| 传统假设 | 新范式 |
|----------|--------|
| 3 人各自讨论，需要合并 | 1 人启动 3 Agent，自动整合 |
| PRD 需要完美才能执行 | Agent 可以处理模糊需求 |
| 讨论结果锁在聊天记录里 | 讨论沉淀为 Skill，可复用 |
| 隐性知识需要人写文档 | Agent 自动从讨论中提取知识 |

**核心转变**：从"人与人协作"转向"人与 Agent 协作"。

---

## 四、Boris 的实践启示

Boris（Claude Code 创始人）的工作方式：

### 4.1 一人多 Agent 模式

```
Boris 的日常：
├── 终端 Claude ×5
├── Web Claude ×5-10
├── 手机启动的会话
└── 总计 15+ 个 Claude 并行

所有会话为 Boris 一人服务
```

这与"多人协作需要 Git 合并"是完全不同的场景。

### 4.2 验证闭环 > 合并分支

Boris 强调的核心：

> **给 Claude 一种验证其工作的方式，质量提升 2-3 倍。**

重点不是"如何合并大家的讨论"，而是"如何让 Claude 自己验证并迭代"。

### 4.3 CLAUDE.md 是集体智慧的沉淀

Boris 团队的做法：
```
发现 Claude 犯错 → 更新 CLAUDE.md → Claude 下次不再犯

Git 同步的不是"讨论记录"，而是"Claude 学到的教训"
```

## 五、重新理解"并行"

### Sam 说的并行

```
Hans ──┐
Dancy ─┼── 各自讨论 ── 需要合并
Petty ─┘
```

### Boris 说的并行

```
Claude 1 ──┐
Claude 2 ──┼── 为同一个人工作 ── 自动协调
Claude 3 ──┘
```

### 关键洞察

> 在 AI 驱动的工作流里，"并行"不再是"多人同时工作"，而是"一个人同时驾驭多个 Agent"。

Git 解决前者（人与人的协作），Claude Code 解决后者（人与 Agent 的协作）。

---

## 六、Git 的新角色

Git 仍然重要，但它的角色变了：

| 传统角色 | 新角色 |
|----------|--------|
| 同步"人的工作产出" | 同步"Skills 和规范文档" |
| 合并"代码分支" | 版本化"可执行的知识" |
| 解决"并行冲突" | 保存"Agent 的学习成果" |

### 应该用 Git 同步什么？

```
✅ 应该同步：
├── Skills 定义（skills/）
├── 规范文档（doc/）
├── SOP（sop/）
├── CLAUDE.md（团队共识）
└── 蓝图文档（blueprint/）

❌ 不需要同步：
├── 每个人的聊天记录
├── 临时讨论文件
└── 中间产物
```

## 七、回到 Sam 的场景

### 场景重述

```
Sam 上传 PRD.md
→ Hans/Dancy/Petty 各自与 Claude 讨论
→ 生成 3 个版本
→ 如何合并？
```

### 表面问题

3 个版本如何合并？（Git 可解决）

### 真正的问题

为什么要 3 个人分别去"讨论"同一份 PRD？

### 更好的方式

```
方案 A（传统思维）：
PRD.md → 3 人各自讨论 → 合并 3 份讨论 → 手动整合

方案 B（Agent 驱动）：
PRD.md → 1 人启动多个 Claude Agent 并行
       → 分别处理架构/用户流程/市场分析
       → Agent 自动整合输出
       → 沉淀为可复用的 Skill
```

## 九、总结

```
Sam 在解决：多人如何合并讨论
更高效的问题：一人如何驾驭多 Agent

Git 解决前者，Claude Code as OS 解决后者
两者不矛盾，但层次不同
```

**一句话**：

> Git 是必要的基础设施，但真正的效率提升来自"从人驱动到 Agent 驱动"的范式转变。
